# Design a feature

Read applicable repository instructions, existing feature records, relevant architecture and domain documentation, and targeted code. Resolve the intended feature and avoid creating a competing record. Treat code inspection, observed runtime behavior, existing intent, and proposed changes as distinct evidence.

Use the repository's feature location and template when available. Otherwise propose a small feature record in an appropriate location. Capture the user outcome, scope, ownership boundaries, contracts and interfaces, failure behavior, security and data implications where relevant, verification, open decisions, and what is already implemented. Identify material uncertainty without blocking independent work. Do not invent approval requirements or change application code unless the user requested it.

For a handoff, give a concise status, decisions that need the owner, and one next action. When useful, provide a ready-to-paste prompt with the feature location, precise scope, relevant evidence, and questions to resolve. Respect the user's request if it also authorizes subsequent planning or implementation.
